# 设计页视图切换内存态重构计划

## 目标

- 将“切换视图”从“保存当前视图状态 + 恢复目标视图状态”调整为“内存态切换 + 只显示激活视图”。
- 保留现有多视图 Fabric Canvas 常驻内存的架构，不改成每次切换时重新挂载或重新初始化。
- 将 `CanvasStateManager` 从“切换流程必经环节”降级为“按需持久化能力”，仅在真正需要落盘或恢复时使用。

## 背景

- 当前多视图初始化阶段已经为每个视图创建独立的 Fabric Canvas，并挂到 `CanvasManager` 中管理。
- 当前视图切换时，DOM 层已经只显示激活的 `.view-container`，隐藏其他视图容器。
- 但是 `store.setActiveViewId()` 仍会调用 `canvasStateIntegration.handleViewSwitch(previousViewId, viewId)`。
- `handleViewSwitch()` 内部会执行：
  - `saveViewState(previousViewId)`
  - `restoreViewState(newViewId)`
- 这导致“切换视图”被耦合为一次 JSON 序列化 / 反序列化流程，增加了 Fabric 对象恢复错误风险。

## 当前实现问题

- 视图切换职责过重：
  - 状态切换
  - DOM 显隐
  - CanvasManager 激活
  - 本地持久化
  - Fabric 对象恢复
- `CanvasStateManager` 更像“页面恢复能力”，但现在被用于高频视图切换。
- 复杂 Fabric 对象在反序列化过程中容易产生结构不一致问题，例如：
  - 文本弧形 `path`
  - `clipPath`
  - 过滤器 / 图片对象内部嵌套结构
- 本地持久化与内存态切换耦合后，不利于排查“切换视图”和“刷新恢复”两类问题。

## 重构原则

- 视图切换只负责“切当前视图”，不负责“重建整个画布”。
- 每个视图的 Fabric Canvas 实例常驻内存，切换时只调整激活态与显示态。
- 页面刷新恢复、购物车编辑恢复、手动草稿保存等能力继续保留，但与普通视图切换解耦。
- 保持现有入口稳定，优先复用：
  - `window.pwcaViewSwitchFacade.switchToView(viewId, options)`
  - `store.setActiveViewId(viewId)`

## 目标行为

- 切换视图时：
  - 更新 `activeViewId`
  - 同步 `activeView`
  - 切换 `layers / layerGroups`
  - 同步印刷方式状态
  - 显示目标 `.view-container`
  - 更新 `CanvasManager` 当前激活画布
  - 更新 `window.canvas` / `window.fabricCanvas`
  - 清理其他画布的选中态
- 不再在普通视图切换中执行：
  - `saveViewState(previousViewId)`
  - `restoreViewState(newViewId)`

## 影响范围

- `modules/front_canvas/assets/js/design/stores/index.js`
- `modules/front_canvas/assets/js/design/utils/canvas-state-integration.js`
- `modules/front_canvas/assets/js/design/utils/canvas-state-manager.js`
- `modules/front_canvas/assets/js/main/view-switch-facade.js`
- 与视图切换相关的外围脚本：
  - `customization-area.js`
  - 图层面板相关脚本
  - 依赖 `layerPanelViewSwitch` 的监听逻辑

## 分阶段计划

## 第一阶段：梳理职责边界

- 明确以下三类能力的边界：
  - 视图切换
  - 状态持久化
  - 外部恢复
- 输出统一结论：
  - “切换视图”不等于“恢复视图状态”
  - `CanvasStateManager` 是持久化工具，不是切换时必须参与的渲染驱动器

## 第二阶段：收紧切换入口

- 以 `pwcaViewSwitchFacade.switchToView()` 作为外围统一切换入口。
- 保持 `store.setActiveViewId()` 负责主状态更新，但减少其中对持久化恢复流程的依赖。
- 确认以下动作仍在单一切换流程中完成：
  - store 激活视图更新
  - DOM 容器显隐
  - `CanvasManager.setActiveCanvas(viewId)`
  - 全局画布引用切换
  - 视图切换事件派发

## 第三阶段：移除切换时的 save / restore

- 从 `store.setActiveViewId()` 中移除对 `canvasStateIntegration.handleViewSwitch()` 的依赖，或让其退化为轻量级同步函数。
- 调整 `canvas-state-integration.js`：
  - 保留画布监听器与 store watcher
  - 去掉“切换时保存前视图 + 恢复新视图”的职责
- 保证切换动作只使用内存中已有的 Fabric Canvas 实例。

## 第四阶段：保留按需持久化能力

- 保留 `CanvasStateManager` 的以下场景：
  - 页面刷新后恢复
  - 离开页面前草稿保存
  - 手动保存草稿
  - 购物车编辑外部状态覆盖
- 梳理触发入口，避免普通切换误触发本地持久化。
- 后续可考虑新增更清晰的 API，例如：
  - `saveDraftState()`
  - `restoreDraftState()`
  - `applyExternalState()`

## 第五阶段：验证依赖链

- 验证以下功能是否仍正确：
  - 多视图切换
  - 图层面板视图同步
  - 工具栏始终作用于当前激活画布
  - 颜色选择按视图隔离
  - 印刷方式映射按视图隔离
  - 页面初始化默认视图显示
  - URL 指定视图定位
  - 购物车编辑回填
  - 加入购物车前导出 / 预览

## 代码改动建议

## 建议一：先改 `store.setActiveViewId()`

- 当前 `setActiveViewId()` 已经负责：
  - 保存当前 `layers / layerGroups` 到 `viewLayers / viewLayerGroups`
  - 更新 `activeViewId`
  - 加载目标视图图层数据
  - 同步印刷方式
- 这里本身已经具备“内存态切换”的主体能力。
- 第一刀建议先删除或封装这段逻辑：
  - `window.canvasStateIntegration.handleViewSwitch(previousViewId, viewId)`

## 建议二：保留 `view-switch-facade.js` 的 DOM 与 CanvasManager 同步职责

- `view-switch-facade.js` 目前已经负责：
  - 隐藏所有 `.view-container`
  - 显示目标视图容器
  - 切换 `CanvasManager` 当前画布
  - 更新 `window.canvas`
  - 清理其他画布选中态
- 这部分应继续保留，作为“只显示激活视图”的主要实现层。

## 建议三：把 `canvas-state-integration.js` 缩成“监听与持久化协调层”

- 该文件可继续负责：
  - 初始化 `CanvasStateManager`
  - 画布事件监听
  - store 变化监听
  - 在明确需要时执行持久化
- 不再负责高频视图切换时的恢复动作。

## 风险点

- 某些旧逻辑可能默认依赖“切换后 restore 一次”来补齐 Store 与 Fabric 对象的一致性。
- 若某些图层状态只存在于 localStorage，而没有真实保留在内存态 store/canvas 中，移除 restore 后可能暴露旧问题。
- 某些外围脚本如果错误依赖了“切换后对象会重新生成”，改成纯内存切换后可能出现时序差异。
- 若存在切换后强制重建对象来修复历史脏数据的隐式逻辑，必须先显式化再移除。

## 验收标准

- 切换视图时控制台不再出现由 JSON 恢复触发的 Fabric 报错。
- 切换视图时不再调用 `saveViewState(previousViewId)` 与 `restoreViewState(newViewId)`。
- 当前视图显示正确，非激活视图隐藏正确。
- 工具栏、图层面板、颜色、印刷方式仍始终对应当前激活视图。
- 刷新页面恢复、购物车编辑恢复等能力仍可独立工作。

## 暂不建议做的事

- 不建议为了实现“只显示激活视图”而把主画布系统整体改造成 Vue 动态组件挂载/卸载模型。
- 不建议直接把 Fabric Canvas 实例放进深响应式状态中。
- 不建议在未梳理恢复入口前，直接删除全部 `CanvasStateManager` 逻辑。

## 推荐实施顺序

1. 先移除视图切换中的 `save/restore` 调用。
2. 验证多视图内存态切换是否稳定。
3. 再把 `CanvasStateManager` 限定为“按需持久化”。
4. 最后补充外部恢复与草稿恢复的独立入口整理。
